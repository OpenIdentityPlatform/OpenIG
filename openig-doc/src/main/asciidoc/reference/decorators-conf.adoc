== Decorators

ifdef::env-site[]
anchor:decorators-conf[]
endif::env-site[]

Decorators add behavior to eligible heap objects. For example, a CaptureDecorator logs requests and responses as they pass through a filter or handler.

To decorate an individual object, add a field named after the decorator alongside the object's `type` and `config` fields. For example, this definition in the `config.json` heap creates a decorator named `capture` and enables entity capture.

[source, json]
----
{
    "name": "capture",
    "type": "CaptureDecorator",
    "config": {
        "captureEntity": true,
        "captureContext": false
    }
}
----
The following ClientHandler configuration would then capture requests including the entity before they are forwarded to the server:

[source, json]
----
{
    "name": "ClientHandler",
    "type": "ClientHandler",
    "capture": "request"
}
----
Add a top-level decorator field to a route to wrap its handler. This example captures requests handled by `ClientHandler` on this route.

[source, json]
----
{
    "handler": "ClientHandler",
    "capture": "request"
}
----
Set the top-level `globalDecorators` field in `config.json`, `admin.json`, or a route to apply a map of decorations when the heap resolves eligible objects. This includes inline objects and references to objects in a parent heap. This example decorates the inline Chain, HeaderFilter, and StaticResponseHandler.

[source, json]
----
{
    "globalDecorators": {
        "capture": "all"
    },
    "handler": {
        "type": "Chain",
        "config": {
            "filters": [
                {
                    "type": "HeaderFilter",
                    "config": {
                        "messageType": "RESPONSE",
                        "add": {
                            "X-Powered-By": [
                                "OpenIG"
                            ]
                        }
                    }
                }
            ],
            "handler": {
                "type": "StaticResponseHandler",
                "config": {
                    "status": 200,
                    "entity": "Hello World"
                }
            }
        }
    },
    "condition": "${matches(request.uri.path, '^/static')}"
}
----
Each decorator applies to supported object types, such as filters and handlers. Decorator objects themselves are excluded.

The gateway heap supplies `baseURI`, `capture`, and `timer`. The administration heap supplies `capture` and `timer`. Reference these names directly or declare a decorator with the same name to override it. See xref:required-conf.adoc#GatewayHttpApplication[GatewayHttpApplication] and xref:required-conf.adoc#admin-json[admin.json].

Choose custom decorator names that do not collide with configuration fields or built-in objects. A dotted name such as `my.decorator` avoids names such as `config`, `name`, and `type` on heap objects, and `condition`, `handler`, `monitor`, and `properties` on routes.

Decorations can apply more than once. For example, if you set a decoration both on a Route and also on an object defined within the route, then OpenIG can apply the decoration twice. The following Route results in the request being captured twice:

[source, json]
----
{
  "handler": {
    "type": "ClientHandler",
    "capture": "request"
  },
  "capture": "all"
}
----
OpenIG wraps objects in this order.

. Apply object-level decorations in the declaring heap at object creation.
. Apply `globalDecorators` from the resolving heap, starting with its ancestors. Look up the decorators in the object's declaring heap and use its heap properties.
. Apply top-level decorations to the resolved handler in the heap that declares the top-level `handler` field.

Each step can add a wrapper around the previous result. An object's local decorations follow it wherever it is used. The `globalDecorators` mappings also apply in descendant heaps.

[#BaseUriDecorator]
=== BaseUriDecorator — override scheme, host, and port of request URI

[#d210e9126]
==== Description
Overrides the scheme, host, and port of the existing request URI, rebasing the URI and so making requests relative to a new base URI. Rebasing changes only the scheme, host, and port of the request URI. Rebasing does not affect the path, query string, or fragment.

[#d210e9136]
==== Decorator Usage

[source, javascript]
----
{
    "name": string,
    "type": "BaseUriDecorator"
}
----
A BaseUriDecorator does not have configurable properties.

OpenIG creates a default BaseUriDecorator named baseURI at startup time in the top-level heap, so you can use baseURI as the decorator name without adding the decorator declaration explicitly.

[#d210e9146]
==== Decorated Object Usage

[source, javascript]
----
{
    "name": string,
    "type": string,
    "config": object,
    decorator name: string
}
----
--

`"name"`: string, required except for inline objects::
The unique name of the object, just like an object that is not decorated

`"type"`: string, required::
The class name of the decorated object, which must be either a Filter or a Handler.

+
See also xref:filters-conf.adoc#filters-conf[Filters] and xref:handlers-conf.adoc#handlers-conf[Handlers].

`"config"`: object, required unless empty::
The configuration of the object, just like an object that is not decorated

__decorator name__: string, required::
A string or string expression supplying the scheme, host, and optional port of the new base URI. OpenIG evaluates an expression for each request with the heap properties and request context.

+
OpenIG ignores non-string values. An expression that evaluates to `null` or yields an invalid URI returns `500 Internal Server Error`.

--

[#d210e9193]
==== Examples
Add a custom decorator to the heap named myBaseUri:

[source, json]
----
{
    "name": "myBaseUri",
    "type": "BaseUriDecorator"
}
----
Set a Router's base URI to `\https://www.example.com:8443`:

[source, json]
----
{
    "name": "Router",
    "type": "Router",
    "myBaseUri": "https://www.example.com:8443/"
}
----

[#CaptureDecorator]
=== CaptureDecorator — capture request and response messages

[#d210e9229]
==== Description
Captures request and response messages at `DEBUG` level. Set the level for `org.forgerock.openig.decoration.capture.CaptureDecorator` in xref:logging-conf.adoc#logging-conf[Logback] to see capture output.

[#d210e9239]
==== Decorator Usage

[source, javascript]
----
{
    "name": string,
    "type": "CaptureDecorator",
    "config": {
        "captureEntity": boolean,
        "captureContext": boolean
    }
}
----
--
The decorator configuration has these properties:

`"captureEntity"`: __boolean, optional__::
Whether the message entity should be captured.

+
Binary entities are logged as `[binary entity]`.

+
Default: false

`"captureContext"`: __boolean, optional__::
Whether to log the contents of `AttributesContext` as JSON. OpenIG excludes the servlet request and response objects from those attributes.

+
Default: false

--

[#d210e9291]
==== Decorated Object Usage

[source, javascript]
----
{
    "name": string,
    "type": string,
    "config": object,
    decorator name: capture point(s)
}
----
--

`"name"`: string, required except for inline objects::
The unique name of the object, just like an object that is not decorated

`"type"`: string, required::
The class name of the decorated object, which must be either a Filter or a Handler.

+
See also xref:filters-conf.adoc#filters-conf[Filters] and xref:handlers-conf.adoc#handlers-conf[Handlers].

`"config"`: object, required unless empty::
The configuration of the object, just like an object that is not decorated

__decorator name__: capture point(s), optional::
The __decorator name__ must match the name of the CaptureDecorator. For example, if the CaptureDecorator has `"name": "capture"`, then __decorator name__ is capture.
+
[open]
====
Use a single string or an array of strings. Capture points are case-insensitive. Each string can be an expression that resolves at configuration time. An empty array skips this decoration. A `null` value or a `null` item is invalid.

`"all"`::
Capture at all available capture points

`"request"`::
Capture the request as it enters the Filter or Handler

`"filtered_request"`::
Capture the request as it leaves the Filter

+
Only applies to Filters

`"response"`::
Capture the response as it enters the Filter or leaves the Handler

`"filtered_response"`::
Capture the response as it leaves the Filter

+
Only applies to Filters

====

--

[#d210e9388]
==== Examples
Decorator configured to log the entity:

[source, json]
----
{
    "name": "capture",
    "type": "CaptureDecorator",
    "config": {
        "captureEntity": true
    }
}
----
Decorator configured not to log the entity:

[source, json]
----
{
    "name": "capture",
    "type": "CaptureDecorator"
}
----
Decorator configured to log the attributes context as JSON:

[source, json]
----
{
    "name": "capture",
    "type": "CaptureDecorator",
    "config": {
        "captureContext": true
    }
}
----
To capture requests and responses with the entity before sending the request and before returning the response, do so as in the following example:

[source, json]
----
{
    "heap": [
        {
            "name": "capture",
            "type": "CaptureDecorator",
            "config": {
                "captureEntity": true
            }
        },
        {
            "name": "ClientHandler",
            "type": "ClientHandler",
            "capture": [
                "request",
                "response"
            ]
        }
    ],
    "handler": "ClientHandler"
}
----
To capture all transformed requests and responses as they leave filters, decorate the Route as in the following example. This Route uses the default CaptureDecorator:

[source, json]
----
{
    "handler": {
        "type": "Chain",
        "config": {
            "filters": [
                {
                    "type": "HeaderFilter",
                    "config": {
                        "messageType": "REQUEST",
                        "add": {
                            "X-RequestHeader": [
                                "Capture at filtered_request point",
                                "And at filtered_response point"
                            ]
                        }
                    }
                },
                {
                    "type": "HeaderFilter",
                    "config": {
                        "messageType": "RESPONSE",
                        "add": {
                            "X-ResponseHeader": [
                                "Capture at filtered_response point"
                            ]
                        }
                    }
                }
            ],
            "handler": {
                "type": "StaticResponseHandler",
                "config": {
                    "status": 200,
                    "reason": "OK",
                    "entity": "<html><p>Hello, World!</p></html>"
                }
            }
        }
    },
    "capture": [
        "filtered_request",
        "filtered_response"
    ]
}
----
To log the attributes context as JSON before sending the request and before returning the response, use the following configuration:

[source, json]
----
{
    "heap": [
        {
            "name": "capture",
            "type": "CaptureDecorator",
            "config": {
                "captureContext": true
            }
        },
        {
            "name": "ClientHandler",
            "type": "ClientHandler",
            "capture": [
                "request",
                "response"
            ]
        }
    ],
    "handler": "ClientHandler"
}
----

[#TimerDecorator]
=== TimerDecorator — record times to process Filters and Handlers

[#d210e9440]
==== Description
Measures elapsed time for filters and handlers. For each timed filter, OpenIG logs the total, internal, and downstream times at `INFO`. For a timed handler, it logs the total at `DEBUG`.

To see handler timings, enable `DEBUG` for `org.forgerock.openig.decoration.timer.TimerDecorator` in xref:logging-conf.adoc#logging-conf[Logback]. The logger name also includes the decorator name and the decorated object's name.

[#d210e9459]
==== Decorator Usage

[source, javascript]
----
{
    "name": string,
    "type": "TimerDecorator",
    "config": {
        "timeUnit": string
    }
}
----

`"timeUnit"`: __string, optional__::
A duration unit with no numeric value. For example, use `milliseconds`, `ms`, or `microseconds`. The default is `milliseconds`.

The built-in `timer` decorator measures in milliseconds.

[#d210e9469]
==== Decorated Object Usage

[source, javascript]
----
{
    "name": string,
    "type": string,
    "config": object,
    decorator name: boolean or boolean expression
}
----
--

`"name"`: string, required except for inline objects::
The unique name of the object, just like an object that is not decorated

`"type"`: string, required::
The class name of the decorated object, which must be either a Filter or a Handler.

+
See also xref:filters-conf.adoc#filters-conf[Filters] and xref:handlers-conf.adoc#handlers-conf[Handlers].

`"config"`: object, required unless empty::
The configuration of the object, just like an object that is not decorated

__decorator name__: boolean or boolean expression, optional::
Set the decoration to `true` to time the object, or `false` to skip this decoration. OpenIG evaluates expressions when it configures the object, using heap properties.

--

[#d210e9531]
==== Examples
Add `timer` to an inline filter and to the route's handler:

[source, json]
----
{
    "condition": "${request.uri.path == '/timed'}",
    "handler": {
        "type": "Chain",
        "config": {
            "filters": [
                {
                    "type": "HeaderFilter",
                    "config": {
                        "messageType": "RESPONSE",
                        "add": {
                            "X-Example": ["timed"]
                        }
                    },
                    "timer": true
                }
            ],
            "handler": {
                "type": "StaticResponseHandler",
                "config": {
                    "status": 200,
                    "entity": "Hello World"
                }
            }
        }
    },
    "timer": true
}
----

This configuration can produce the following messages when handler timing logs are enabled:

[source,text]
----
INFO  Elapsed time: 40 ms (internal: 1 ms, downstream: 39 ms)
DEBUG Elapsed time: 41 ms
----
