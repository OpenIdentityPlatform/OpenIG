== Configuring Routes

ifdef::env-site[]
anchor:chap-routing[]
endif::env-site[]

Other tutorials in this guide demonstrate how to use routes so that you can change the configuration without restarting OpenIG. This chapter takes a closer look at `Router` and `Route` configurations, further described in xref:../reference/handlers-conf.adoc#Router[Router(5)] in the __Configuration Reference__ and xref:../reference/handlers-conf.adoc#Route[Route(5)] in the __Configuration Reference__. In this chapter, you will learn to:

* Protect multiple routes with the same OpenIG server

* Lock down OpenIG configurations for deployment


[#routing-router-setup]
=== Configuring Routers

When you set up the first tutorial, you configured a `Router`.

Configure the `Router` as the top-level handler in `config.json`, as shown in xref:chap-quickstart.adoc#quickstart-configure[Configure OpenIG]. You can also use a router wherever a handler is accepted.

The router checks the route directory at startup. It then scans for additions, changes, and removals on a schedule, even when OpenIG receives no requests. The default directory is `config/routes` under the OpenIG base directory. The default scan interval is `"10 seconds"`.

[#routing-route-setup]
=== Configuring Additional Routes

Routes are configurations to handle a request that meets a specified condition.

The condition is defined using an OpenIG expression as described in xref:../reference/expressions-conf.adoc#Expressions[Expressions(5)] in the __Configuration Reference__. It can be based on almost any characteristic of the request, context, or even of the OpenIG runtime environment. Another way to think of the `Route` is like an independent `DispatchHandler` as described in xref:../reference/handlers-conf.adoc#DispatchHandler[DispatchHandler(5)] in the __Configuration Reference__.

This route condition matches requests with `api.example.com` as the URI host:

[source,javascript]
----
"condition": "${request.uri.host == 'api.example.com'}"
----
The router checks routes in lexicographic order by route ID and dispatches to the first match. For JSON route configurations, the ID is the filename without `.json`. The optional `name` field sets the display name. With OpenAPI support enabled, the router also discovers specifications with the `.json`, `.yaml`, and `.yml` extensions. See xref:../reference/handlers-conf.adoc#Router[Router] for how OpenAPI route IDs are assigned.

Routes can have a base URI to change the scheme, host, and port of the request.

Routes wrap a heap of configuration objects, and hand off any request they accept to a handler. In this way each route is much like its own server-wide configuration file.

An omitted or null `condition` makes the route unconditional. If a configured condition evaluates to false or null for a request, the router continues looking for a match. Save an unconditional route with a filename that sorts after the other route IDs, such as `99-default.json`, so it serves as a fallback.

[source, json]
----
{
    "name": "Fallback",
    "baseURI": "http://127.0.0.1:8081",
    "handler": {
        "type": "ClientHandler"
    }
}
----


[#routing-lockdown]
=== Locking Down Route Configurations

Having the `Route` configurations automatically reloaded is great in the lab, but is perhaps not what you want in production.

Set the router's `scanInterval` to `"disabled"` to load routes only at startup, then restart OpenIG. Use a duration string such as `"30 seconds"` to set an explicit scan interval. See xref:../reference/handlers-conf.adoc#Router[Router(5)] for the supported values.

[source, json]
----
{
    "name": "Router",
    "type": "Router",
    "config": {
        "scanInterval": "disabled"
    }
}
----
You can also change the file system location to look for routes:

[source, json]
----
{
    "name": "Router",
    "type": "Router",
    "config": {
        "directory": "/path/to/safe/routes",
        "scanInterval": "disabled"
    }
}
----
